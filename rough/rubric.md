# Stage 2 and 4 Marking Rubric

| Dimension | Sophisticated | Highly Competent | Fairly Competent | Competent | Lacking Competency |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Marks** | **100/100** | **80/100** | **60/100** | **50/100** | **30/100** |
| **Programming constructs to model hardware (4%)** | Single line assign statements and multi-line process blocks with behavioral modeling | A few multi-line process blocks can be rewritten as single line assign statements for conciseness using behavioral modeling | Most combinational logic modelled either using assign or as process | Most combinational logic modelled either using assign or as process and mixing behavioral and gate-level modeling in assign | All combinational logic modelled either using assign or as process and mixing behavioral and gate-level modeling in assign |
| **Sensitivity list for processes (5%)** | Necessary and sufficient signals constituting sensitivity list for all processes | Necessary and sufficient signals constituting sensitivity list for most processes; for remaining processes, sensitivity list has more signals than necessary | Few processes have sensitivity list set to `*` (sensitive to all signals) | Most processes have sensitivity list set to `*` | All processes have sensitivity list set to `*` |
| **Latch inferences (8%)** | No latch inference for any processes; case statements/if-else have default case and all cases covered | Some case statements/if-else do not have all cases covered but signal is assigned a default value that preserves functionality | Design code does not adhere to synthesizable hardware | Some latch inference present; some case statements/if-else do not cover all cases | Design code does not adhere to synthesizable hardware |
| **Synthesizable hardware (15%)** | Design code adheres to synthesizable hardware | Design code adheres to synthesizable hardware | Some signals have initial value set to X or for loops with dynamic loop count, signal assignment at declaration | Some signals have initial value set to X or for loops with dynamic loop count, signal assignment at declaration | Design code does not adhere to synthesizable hardware |
| **Process definitions (5%)** | • Use `always_comb` for combinational and `always_ff` for sequential and correct usage of non-blocking and blocking semantics<br>• Number of lines per process is at most 10 | • Few (2–3) instances of `always` for combinational with correct usage of non-blocking and blocking semantics<br>• Number of lines per process is between 10–20 | • Few (2–3) instances of `always` for combinational with incorrect usage of non-blocking and blocking semantics<br>• Number of lines per process is between 10–20 | • Most instances of `always` for combinational with correct usage of non-blocking and blocking semantics<br>• Number of lines per process is beyond 20 | • Most instances of `always` for combinational and incorrect usage of non-blocking and blocking semantics<br>• Number of lines per process is beyond 20 |
| **Datapath design (8%)** | Each datapath component (register, memory) has asynchronous reset logic | Each datapath component (register, memory) has synchronous reset logic | Some datapath components have reset logic | Some datapath components have mix of synchronous and asynchronous reset logic | No datapath components have reset logic |
| **Constants (3%)** | All constants defined in a separate file and reused; appropriate names for constants | Most constants defined in a separate file and reused; appropriate names for constants | Most constants defined but not housed in a separate file (define-and-immediate-use style) with limited reuse; satisfactory names for constants | Some constants defined and limited reuse; poor naming for constants | No constants defined and used |
| **Signals, variables and processes names (3%)** | • All signals, temporaries and processes have appropriate and descriptive names<br>• Consistent naming style (camel casing or underscore style) | • All signals, temporaries and processes have appropriate and descriptive names<br>• Mixed naming style | • Most signals, temporaries and processes have appropriate and descriptive names<br>• Consistent naming style | • Some signals, temporaries and processes have appropriate and descriptive names<br>• Consistent naming style | • Few signals, temporaries and processes have appropriate and descriptive names<br>• Consistent/mixed naming style |
| **SystemVerilog (SV) extensions (2%)** | Extensive use of SV extensions such as tasks, functions, and assertion checkers | — | Limited use of SV extensions such as tasks, functions, and assertion checkers | — | No use of SV extensions |
| **Testbench design (30%)** | Exhaustive coverage with clear tests for trivial cases, corner cases, invalid cases, and non-trivial sequences | Exhaustive coverage with clear tests for trivial, corner, and invalid cases | Exhaustive coverage with clear tests for trivial and most corner cases | Coverage with tests for some trivial and corner cases | No testing or barebones testing with few cases |
| **Code comments (7%)** | • Descriptive comments for all signals and variables<br>• Descriptive comments describing each process logic<br>• Correct grammar<br>• TODO placeholders for thoughts on future extensions and optimizations | • Descriptive comments for all signals and variables<br>• Descriptive comments describing each process logic<br>• Correct grammar | • Descriptive comments for most signals and variables<br>• Descriptive comments describing most process logic | • Descriptive comments for some signals and variables<br>• Descriptive comments describing some process logic | • No comments / insufficient descriptive comments for signals and process logic |
| **Code revisioning (5%)** | • Use of git to revision control code<br>• Adhering to proper code commit practice — branch, code review, merge to main branch<br>• Descriptive commit messages<br>• Setup continuous integration (CI) for automated testing for code check-ins to main branch | • Use of git to revision control code<br>• Adhering to proper code commit practice — branch, code review, merge to main branch<br>• Descriptive commit messages | • Use of git to revision control code<br>• Adhering partially to proper code commit practice — branch, limited/no code review, merge to main branch | • Use of git to revision control code | • No revision control |
| **Delegation and fulfillment of responsibilities (3%)** | • Responsibilities delegated fairly from beginning<br>• Clear division of work from beginning<br>• Deadlines met for all project deliverables | • Responsibilities delegated fairly from beginning<br>• Clear division of work from beginning<br>• Deadlines met for most project deliverables | • Responsibilities delegated fairly over time<br>• Clear division of work over time<br>• Deadlines met for all project deliverables | • Responsibilities delegated fairly over time<br>• Clear division of work over time<br>• Deadlines met for some project deliverables | — |
| **Team morale and cohesiveness (2%)** | • Camaraderie among teammates<br>• High team morale and enthusiasm<br>• Mutual respect<br>• No issues raised with instructor regarding teammates' work and commitment | • Camaraderie among teammates<br>• High team morale and enthusiasm<br>• Mutual respect<br>• Issues raised regarding teammates' work and commitment and resolved within team | • Camaraderie among teammates<br>• High team morale and enthusiasm<br>• Mutual respect<br>• Issues raised regarding teammates' work and commitment and resolved after consulting with instructor | • Moderate camaraderie, morale and enthusiasm<br>• Issues solved either among teammates or on consultation with instructor | — |
